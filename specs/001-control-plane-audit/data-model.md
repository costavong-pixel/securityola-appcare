# BETA-01 Control Plane Data Model

## Cross-cutting rules

- All identifiers are opaque, non-sequential public IDs generated by the AppCare service.
- Every tenant-owned entity carries `tenant_id` and is queried through the authenticated tenant context.
- Tenant-owned records use created/updated timestamps and explicit lifecycle status where applicable.
- Foreign keys are enforced. Cross-tenant relationships are rejected before persistence and covered by negative tests.
- Secret-bearing values are never persisted in clear text, returned in API responses, written to logs, or copied into audit metadata.
- Audit events are append-only, sanitized, hash-linked, and protected against update/delete at the database boundary.

## Identity and ownership

### Tenant

- `id`, `name`, `status`, `created_at`, `updated_at`
- Owns users and all customer resources.
- Status values: `active`, `suspended`, `disabled`.

### User

- `id`, `tenant_id`, `email`, `display_name`, `password_hash`, `status`, `last_authenticated_at`, `created_at`, `updated_at`
- Email is unique within a tenant; password hashes are one-way and never returned.
- Status values: `active`, `disabled`.

## Customer resources

### Application

- `id`, `tenant_id`, `name`, `repository_url`, `environment`, `status`, `created_at`, `updated_at`
- `environment` is descriptive (`development`, `staging`, `production`) and does not grant production access.

### Asset

- `id`, `tenant_id`, `application_id`, `kind`, `locator`, `status`, `created_at`, `updated_at`
- Locator values are sanitized references only; credentials and secret-bearing URLs are rejected.

### Finding

- `id`, `tenant_id`, `application_id`, `asset_id`, `severity`, `status`, `title`, `summary`, `fingerprint`, `created_at`, `updated_at`
- Finding ownership must match the application and optional asset ownership.

## Operational records

### Connector

- `id`, `tenant_id`, `application_id`, `provider`, `kind`, `status`, `display_name`, `last_checked_at`, `created_at`, `updated_at`
- Descriptive only in BETA-01; no access token or executable operation is stored.

### Job

- `id`, `tenant_id`, `application_id`, `kind`, `status`, `retry_count`, `cost_amount`, `cost_currency`, `queued_at`, `started_at`, `finished_at`, `failure_code`, `failure_message`, `created_at`, `updated_at`
- Retry count is non-negative; cost is non-negative and uses a fixed precision representation; status transitions are allowlisted.

### Backup

- `id`, `tenant_id`, `application_id`, `status`, `provider`, `artifact_reference`, `verified_at`, `failure_code`, `created_at`, `updated_at`
- Artifact references are opaque and cannot contain credentials; no backup provider is called in BETA-01.

### Approval

- `id`, `tenant_id`, `application_id`, `kind`, `status`, `requested_by`, `decided_by`, `decision_reason`, `requested_at`, `decided_at`, `created_at`, `updated_at`
- Approval state is recorded for later workflows; it does not authorize a deployment in this phase.

### Deployment

- `id`, `tenant_id`, `application_id`, `environment`, `status`, `requested_by`, `approved_by`, `revision`, `failure_code`, `created_at`, `updated_at`
- Descriptive intent/status only; no provider call, credential, or production execution method exists.

## Audit integrity

### Audit Event

- `id`, `tenant_id`, `actor_user_id`, `action`, `subject_type`, `subject_id`, `outcome`, `metadata_json`, `occurred_at`, `previous_event_hash`, `event_hash`
- `metadata_json` is recursively sanitized and bounded; values matching secret-like keys or credentials are rejected/redacted.
- `event_hash` covers the immutable event fields and previous tenant event hash.
- Application update/delete operations are absent; database triggers reject direct update/delete attempts. Trigger installation failure prevents startup.

## Relationships and invariants

- Tenant 1-to-many User, Application, Asset, Finding, Connector, Job, Backup, Approval, Deployment, and Audit Event.
- Application belongs to one Tenant; every child resource must match the application Tenant.
- Asset and Finding may reference an Application only within the same Tenant.
- Audit Event actor belongs to the event Tenant; actor may be absent only for explicitly system-generated local events.
- No entity has a relationship to WordPress Security resources, production credentials, deployment sockets, or external provider clients.

## State rules

- User/Tenant status transitions are explicit and reject disabled actors.
- Job status transitions are monotonic through `queued → running → succeeded|failed|cancelled`; retry count increases only through a service operation.
- Approval status is `requested → approved|rejected|expired` and is audit-recorded.
- Backup/Deployment/Connector statuses are descriptive and cannot trigger external work.
